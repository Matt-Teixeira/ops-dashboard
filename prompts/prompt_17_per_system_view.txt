Phase 17 - Per-System (Equipment) Correlation View

Goal:
Reframe the dashboard around the physical equipment system, not just the app. The same
system (identified by note.sme, e.g. SME20487) surfaces warnings/errors across MULTIPLE
apps -- data_acquisition (the pull) and the hhm_rpp_* parsers (the downstream parse) --
but today those signals are only ever shown per-app, so an operator can't see one
system's whole story or tell root cause from downstream noise. Add a read-only,
cross-app per-system view: a worst-first LIST of systems with recent issues, and a
per-system DETAIL that breaks its issues down by (app, type, func) and joins the
classified connectivity state. This is the "deeper relationship" between the monitoring
data and the apps it watches -- surfaced as insight for a human, never a write-back.

Background (verified live this session - do not re-discover):
- util.app_run_logs.warn_error_logs and verbose_log are `json` (NOT jsonb) -> use
  json_array_elements and ->/->> ; no jsonb operators (@>, jsonb_array_elements).
- The system key in an event is `note->>'sme'` ONLY. `note->'system'->>'id'` is never
  populated (0/166k events in 7d) -- do NOT add it as a fallback.
- error_category is NOT reliably in the run-log note: only 625/166k data_acquisition
  events carry it and the only 7d value was "hanging_exec". The real classified enum
  (connection_timeout, max_retries, rsync_io_timeout, credentials, host_key_changed,
  connection_reset, host_unreachable, partial_transfer_timeout, session_timeout,
  key_exchange, host_key_new, file_missing_partial, ...) lives in the alert.* tables
  (alert.offline_hhm_conn / offline_mmb_conn), one row per system. So: use `func` as the
  in-log grouping axis, and JOIN the alert.* state (already read by /api/connectivity)
  for the classified category in the detail view.
- Cross-app correlation is real: e.g. SME20487, SME16421, SME16411 each appear in BOTH
  data_acquisition and hhm_rpp_philips in 7d; many systems span 2 apps.
- Volume/perf (system-keyed warn/error events, LATERAL unnest of warn_error_logs only --
  NO verbose_log detoast): 24h ~ 227 systems in ~150ms; 7d ~ 241 systems in ~2.2s.
  EXPLAIN confirms partition pruning: Index Scan on app_run_logs_2026_06_inserted_at_idx
  with `inserted_at > $1`. -> default window 24h, clamp max 168h (7d is the slow ceiling);
  request-path direct like connectivity/acq (no cache, no detoast).
- No new grant: this reads util.app_run_logs (already granted) + alert.* (granted in
  Phase 10). Unlike Phase 15 there is NO setup-readonly-role.sql / deploy grant step.

Scope:
- Query in db/queries.js:
  - SYSTEMS_LATEST_SQL + systemsLatest(sinceIso, limit): per note.sme across ALL apps in
    the window -> issues=count(*), errors=count FILTER type='ERROR', warns=count FILTER
    type='WARN', apps=count(DISTINCT app_name), which=string_agg(DISTINCT app_name),
    last_seen=to_char(max(inserted_at)...). WHERE inserted_at > $1::timestamptz; unnest
    warn_error_logs via LATERAL json_array_elements; WHERE sme IS NOT NULL; GROUP BY sme;
    ORDER BY errors DESC, issues DESC, sme; LIMIT $2. No verbose_log.
  - SYSTEM_DETAIL_SQL + systemDetail(systemId, sinceIso): for one sme -> GROUP BY
    (app_name, type, func) with n=count(*), last_run_id=(array_agg(run_id ORDER BY
    inserted_at DESC))[1], last_inserted_at=to_char(max(inserted_at)...). The sme is a
    BOUND param ($1), never interpolated. Same window filter + unnest; no verbose_log.
    ORDER BY (type='ERROR') DESC, n DESC, app_name, func.
- lib/systems.js (server-only, pure; mirrors lib/acq.js / lib/connectivity.js):
  - shapeSystems(rows) -> camelCase list incl. apps split of `which` into an array.
  - summarize(rows) -> { systems, errors, warns, crossApp } (crossApp = # systems in >1
    app) for the list header.
  - shapeDetail(rows) -> camelCase breakdown rows (app, type, func, count, lastRunId,
    lastInsertedAt).
  - pickSystem(decoratedConnectivity, systemId) -> the connectivity rows (HHM/MMB) for
    that system, reusing connectivity.decorate output. Pure.
  All unit-tested.
- server.js:
  - GET /api/systems?windowHours=<n> (clamp via appRunsLib.clampInt, default env
    SYSTEMS_WINDOW_HOURS=24, 1..168) -> { windowHours, asOf, count, summary, systems }.
  - GET /api/systems/:id?windowHours=<n> -> validate id against a strict shape
    (/^[A-Za-z0-9_-]{1,64}$/, 400 otherwise), clamp window -> { systemId, windowHours,
    asOf, connectivity, breakdown }. connectivity from queries.connectivity() decorated
    + systems.pickSystem. Thin handlers; errors via the shared sanitized 500.
- public/index.html:
  - Add a "systems" link in the top nav (next to "connectivity").
  - Add #systems (list) and #system=<id> (detail) routed views. Introduce a
    hideAllViews() helper (hides every view section) so each show* function -- new and
    existing -- can't leave a stale sibling visible now that there are 7 views; replace
    the repeated per-function hide blocks with it (behavior-preserving cleanup).
  - List: worst-first table (System, Errors, Warns, Apps, Last seen); rows with errors>0
    get .row-ERROR; each System links to #system=<id>; header shows summary (systems,
    crossApp).
  - Detail: header (system id, window, connectivity status/category from alert.*), then a
    breakdown table (App, Type, Func, Count, latest run -> drill-down via runHref using
    lastRunId + lastInsertedAt hint). Text via textContent; reuse backLink/connMessage/
    cell/fmtTime/runHref + the runReq guard + show/hide.
  - Cross-link INTO the detail: make the System id in the connectivity and acquisition
    views link to #system=<id>.
- Config: SYSTEMS_WINDOW_HOURS in .env.example + markdown/ENVIRONMENT.md.

Non-goals:
- No writes; no auto-remediation; no changes to the OTHER apps' repos. Read-only insight
  only.
- No error-category analytics/trends over time (that is Phase 18) and no actionable
  error->owner mapping (Phase 20). This phase is the correlation backbone only.
- No new grant/schema/index; no cache (served direct); no pagination (list LIMIT 500,
  worst-first, in a bounded window).
- Do not read verbose_log on the request path; do not add note.system.id or
  error_category-from-note as axes (verified absent/unreliable).
